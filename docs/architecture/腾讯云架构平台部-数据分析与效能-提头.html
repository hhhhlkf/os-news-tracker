[RFC] Reconsider sysupdate worker process visibility + features
GitHub 消息
AdrianVovk · 08-24 00:12 · 父节点已选中
我们的计划是让 systemd-sysupdate 作为仅处理单个 target（组件、--root、--directory 等）的无状态 worker，而由 updatectl 作为面向用户的控制器，负责记录有哪些目标、将每个目标暴露给前端，并支持独立、并行的更新。v261 中，systemd-sysupdate 被移入 /usr/bin，因而意外成为稳定 API；v262 主分支新增的 --component-all / --component-suggested 开关可用于 update、vacuum 等操作。这与 updatectl / Varlink 化的既定计划相冲突。如果 sysupdate 不能移回 /usr/lib/systemd，--component-all 就会稳定下来，形成一条完整但仅命令行可用的替代路径。它无法像 updatectl 那样面向 GUI 集成，也会让 hook 脚本和功能实现出现两套不一致的处理方式。理想情况下应回退前者；若无法回退，也应避免稳定化后者。这样才能在 updatectl 完成后保留单一实现路径，并为 vmspawn 虚拟机等未来多目标更新能力留出一致的扩展空间。
