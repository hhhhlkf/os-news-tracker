# 开发邮件列表实时订阅入口调研

> 调研日期：2026-08-14  
> 范围：仅核查项目/列表运营方的一手页面；目标是区分历史归档与可持续获得新邮件的入口。

## 结论

“归档”不等于停更：对仍由 Mailman 驱动的项目，应把 **订阅后的邮箱（用 IMAP/Webhook 摄取）** 作为实时源，把网页归档仅作为回补和历史检索源。不要轮询归档页面来模拟实时邮件。

| 项目 | 当前实时入口 | 开发协作重心 | 采集建议 |
| --- | --- | --- | --- |
| systemd | [systemd-devel 订阅页](https://lists.freedesktop.org/mailman/listinfo/systemd-devel)，`systemd-devel@lists.freedesktop.org` | **混合，GitHub PR/Issue 为变更主流程；邮件列表仍用于技术讨论/一般问题** | 保留列表订阅；以 [GitHub PR](https://github.com/systemd/systemd/pulls) 与 [Issues](https://github.com/systemd/systemd/issues) 为主信号。 |
| glibc 开发 | [libc-alpha 订阅页](https://sourceware.org/mailman/listinfo/libc-alpha)，`libc-alpha@sourceware.org` | **邮件列表驱动** | 订阅邮箱；归档只回补。 |
| glibc 稳定修复 | [libc-stable 订阅页](https://sourceware.org/mailman/listinfo/libc-stable)，`libc-stable@sourceware.org` | **邮件列表驱动（稳定分支回补/提交流）** | 订阅邮箱；适合跟踪 backport 与稳定分支提交。 |
| GCC | [gcc-patches 订阅页](https://gcc.gnu.org/mailman/listinfo/gcc-patches)，`gcc-patches@gcc.gnu.org` | **邮件列表驱动** | 订阅邮箱；量大，按 `List-Id` 和主题串聚合。 |
| LLVM/Clang | [LLVM Discourse](https://discourse.llvm.org)；按类别订阅邮件，例如 Clang 为 `clang@discourse.llvm.org` | **Discourse 驱动，保留邮件交互** | 不再将 `llvm-dev` 作为实时列表；订阅相关 Discourse 分类，或使用其 API/RSS/邮件通知。 |
| QEMU | [qemu-devel 订阅页](https://lists.nongnu.org/mailman/listinfo/qemu-devel)，`qemu-devel@nongnu.org` | **邮件列表驱动** | 订阅邮箱；这是补丁评审、合并的主线。 |
| runc | [runc GitHub 仓库](https://github.com/opencontainers/runc) 的 Watch/Issues/PRs/Discussions 通知 | **GitHub 驱动** | 用 GitHub API/Webhook 或账户 Watch 邮件；不应把“runc 邮件列表”作为数据源。 |

## 逐项依据与接入要点

### systemd / systemd-devel

官方 Mailman 页面明确称 `systemd-devel` 为“主要 systemd 邮件列表”和技术讨论场所，提供网页表单订阅与投递地址；该列表要求通过网页表单订阅，且发信者需先订阅。[systemd-devel 官方订阅页](https://lists.freedesktop.org/mailman/listinfo/systemd-devel)

不过 systemd 的贡献指南把 bug 与功能请求**专门**放在 GitHub Issues，并规定代码改动走 GitHub Pull Request；同页仍把 `systemd-devel` 指向一般 systemd 问题。因此，对于趋势采集，它应是“实时但非唯一、且不宜作为提交主线”的源。[systemd Contributing](https://systemd.io/CONTRIBUTING/)

### glibc / libc-alpha、libc-stable

两个列表均为可写入、可网页订阅的 Sourceware Mailman 列表：`libc-alpha` 的投递地址是 `libc-alpha@sourceware.org`，[订阅页](https://sourceware.org/mailman/listinfo/libc-alpha)；`libc-stable` 则是 `libc-stable@sourceware.org`，[订阅页](https://sourceware.org/mailman/listinfo/libc-stable)。两页都提供确认订阅和可选日摘要，说明它们不是单纯档案。

glibc 的官方参与页进一步定义前者用于 glibc 开发讨论，后者用于稳定分支回补讨论，并说明后者会接收稳定发布分支的 git 提交流；因此 `libc-stable` 对发行版维护和回补趋势尤其有价值。[glibc Get involved](https://sourceware.org/glibc/involved.html)

### GCC / gcc-patches

`gcc-patches` 有可用的 Mailman [订阅页](https://gcc.gnu.org/mailman/listinfo/gcc-patches)：填写邮箱后确认即可，也可选日摘要；投递地址为 `gcc-patches@gcc.gnu.org`。GCC 的官方列表说明把它定义为补丁提交及具体补丁讨论的高流量列表，并说明可使用 RFC 2369 的 `List-*` 头（含 `List-Id`）过滤邮件。[GCC mailing lists](https://gcc.gnu.org/lists.html)

### LLVM / Clang

`llvm-dev` 是历史名称，不应再按 Mailman 实时列表接入。LLVM 的现行迁移指南明确说其目的在于从邮件列表迁往 Discourse；旧列表会只读，Mailman 归档会保留。当前 Discourse 地址为 [discourse.llvm.org](https://discourse.llvm.org)，它可对类别/主题订阅并通过邮件接收和回复；Clang Frontend 分类的发帖地址为 `clang@discourse.llvm.org`。[LLVM Discourse Migration Guide](https://llvm.org/docs/DiscourseMigrationGuide.html)

因此，若目标是 LLVM/Clang 的前沿设计讨论，应订阅 `Clang Frontend`、`IR & Optimizations`、目标后端等分类，而不是只保留已归档的 `llvm-dev`。

### QEMU / qemu-devel

`qemu-devel` 的 [官方订阅页](https://lists.nongnu.org/mailman/listinfo/qemu-devel) 提供确认订阅，投递地址为 `qemu-devel@nongnu.org`。更关键的是，QEMU 官方补丁指南明确写明项目使用公开的邮件式工作流，所有贡献都必须以补丁邮件发至 `qemu-devel`；虽然不订阅也可发起线程，但订阅有助于获取其他帖子的想法，并警告该列表常一周超过一千封邮件。[QEMU Submitting a Patch](https://www.qemu.org/docs/master/devel/submitting-a-patch.html)

这应作为最高优先级的实时邮件源；按 patch series、`Message-Id` 和 `In-Reply-To` 合并，而不是逐封入库。

### runc

runc 的官方贡献指南要求先创建 GitHub enhancement issue，再提交 GitHub PR；评审意见和追加提交也在 PR 上进行。文档唯一指定的邮件地址是私密安全报告 `security@opencontainers.org`，不是公开技术讨论列表。[runc CONTRIBUTING.md](https://github.com/opencontainers/runc/blob/main/CONTRIBUTING.md)

所以 runc 应改为 GitHub 实时流：仓库 Watch 邮件适合个人订阅，产品采集则优先 GitHub API/Webhook（Issues、Pull Requests、Reviews、Comments、Releases；Discussions 可作为辅助）。公开 [Discussions](https://github.com/opencontainers/runc/discussions) 存在，但不应替代 Issue/PR 事件作为实现进展证据。

## 实施边界

- “实时邮件”需要一个授权邮箱订阅这些列表，再从该邮箱的 IMAP/邮件转发 webhook 读取；仅有公开归档 URL 无法稳定提供推送语义。
- 高流量列表（特别是 QEMU、GCC）先做线程归并与补丁系列归并，再交给事件/趋势层；否则转发、`[PATCH n/m]` 与评审会严重放大计数。
- GitHub/Discourse 项目应保留其原生事件 ID、更新时间和讨论/PR 关联；不要强行伪装成邮件列表条目。
