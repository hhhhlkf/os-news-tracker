# 新闻流手动处理控制面板设计

- 文档日期：2026-06-11
- 状态：待用户评审
- 作用范围：`os-news-tracker` 首页新闻流手动任务控制

---

## 1. 目标

在现有首页顶部增加一个简约、清晰的控制条，用来手动控制一轮**新闻流**处理任务。

这轮任务需要支持：

- 显式开始处理
- 显式结束处理
- 选择新闻时间范围
- 限制本轮候选抓取条数
- 展示简要任务状态与进度

本设计只覆盖**新闻流**（`rss` / `page_monitor` / `search`），不扩展到结构化流。

---

## 2. 已确认约束

| 维度 | 结论 |
| --- | --- |
| 控制对象 | 新闻流任务，不包含结构化流 |
| 大模型开关语义 | 不是单纯是否做富化，而是控制一轮完整任务的开始与结束 |
| 时间范围 | 同时支持相对时间范围和绝对时间范围 |
| 默认时间交互 | 默认使用相对时间范围，必要时切到绝对范围 |
| 条目数语义 | 限制本次抓取进入处理队列的候选新闻上限 |
| 放置位置 | 首页顶部，与现有统计卡同层展示 |
| 状态反馈 | 简要进度：状态、已抓取数、已处理数、时间范围 |

---

## 3. 非目标

本次不做：

- 结构化流手动任务控制
- 任务历史列表
- 多任务并发执行
- 来源级别进度明细
- 失败重试中心
- MCP 内网站点抓取接入
- 复杂权限控制或多用户任务隔离

---

## 4. 用户体验设计

### 4.1 位置

控制条放在首页 header 区域下方、搜索框上方，和当前统计卡属于同一层级，但视觉上独立成一条操作带。

这样用户一进页面就能看见：

- 当前是否可手动发起处理
- 本轮处理会抓什么范围
- 当前任务是否在跑

### 4.2 布局

控制条由 4 个区域组成：

1. **任务主按钮区**
   - 空闲时显示 `开始处理`
   - 运行中显示 `结束处理`
   - 停止中显示禁用态 `停止中`

2. **时间范围区**
   - 分段控件：`24h` / `7d` / `30d` / `自定义`
   - 选中 `自定义` 时显示开始日期和结束日期输入

3. **候选条目上限区**
   - 数字输入框
   - 默认建议值：`50`

4. **状态反馈区**
   - 任务状态
   - 已抓取数量
   - 已处理数量
   - 当前生效时间范围摘要

### 4.3 视觉要求

- 维持当前首页已有的克制风格
- 不做第二套“筛选栏”视觉
- 操作区使用浅底、细边框、紧凑间距
- 主按钮清晰，但不过分抢占 header
- 数字输入与日期输入宽度固定，避免状态切换时跳动

## 5. 前端行为设计

### 5.1 本地表单状态

前端新增一个“手动处理任务”表单状态，字段如下：

- `timeMode`: `relative | absolute`
- `relativeRange`: `24h | 7d | 30d`
- `startDate`: `string | null`
- `endDate`: `string | null`
- `candidateLimit`: `number`

### 5.2 任务状态来源

任务状态不由前端自行推测，而由后端返回统一任务状态。

前端通过轮询状态接口获得：

- 当前是否有运行中的新闻流任务
- 当前任务配置
- 已抓取数量
- 已处理数量
- 任务状态

### 5.3 按钮行为

#### 开始处理

点击 `开始处理` 时：

1. 校验时间范围输入是否合法
2. 校验 `candidateLimit > 0`
3. 调用后端“启动任务”接口
4. 成功后切换到轮询任务状态

#### 结束处理

点击 `结束处理` 时：

1. 调用后端“停止任务”接口
2. 按钮进入 `停止中`
3. 后端任务在安全边界停止
4. 前端继续轮询，直到状态变成 `stopped` 或 `completed`

### 5.4 列表与控制条关系

控制条不直接替换当前列表查询逻辑。它的职责是触发一轮处理任务，任务产出的新条目自然进入现有列表。

也就是说：

- 控制条管“生产”
- 搜索和筛选区域管“消费”

这两个区域应保持职责分离。

## 6. 后端任务模型

### 6.1 总体策略

后端增加一个**单活新闻流任务控制器**。

任意时刻只允许一轮手动新闻流任务处于活动状态。这样可以避免：

- 多轮手动抓取互相抢 source
- 进度混杂
- 停止语义不明确

### 6.2 任务状态

状态集合：

- `idle`
- `running`
- `stopping`
- `completed`
- `failed`
- `stopped`

### 6.3 任务配置字段

- `time_mode`
- `relative_range`
- `start_at`
- `end_at`
- `candidate_limit`
- `started_at`
- `finished_at`

### 6.4 任务进度字段

- `fetched_count`
- `processed_count`
- `last_error`

这些字段先允许以内存单例方式存在于应用进程内，不强制首版持久化到数据库。

理由：

- 本功能首先是一个开发和运营控制工具
- 当前项目还没有任务历史或多实例协调需求
- 先以内存状态实现可以明显降低范围与复杂度

后续如果要支持多实例、任务历史或进程重启恢复，再迁移到数据库表。

## 7. 手动新闻流任务执行规则

### 7.1 覆盖范围

只遍历 `sources.stream = news` 的来源，并仅处理当前已支持的新闻抓取类型：

- `rss`
- `page_monitor`
- `search`

### 7.2 执行流程

1. 接收前端任务参数
2. 构建一轮手动新闻流上下文
3. 遍历启用中的新闻源
4. 抓取候选内容
5. 依据所选时间范围过滤候选
6. 将候选截断到 `candidate_limit`
7. 对保留下来的候选执行现有处理链
   - extract
   - normalize
   - dedup
   - enrich
   - store
8. 更新进度
9. 完成后写入最终状态

### 7.3 时间范围语义

#### 相对时间范围

相对范围以“当前任务启动时间”为基准向前回看：

- `24h`
- `7d`
- `30d`

#### 绝对时间范围

前端提供开始日期和结束日期，后端转换为明确的闭区间时间窗口。

若候选内容没有 `published_at`，默认不纳入“时间范围受控”的手动任务结果。

理由：

- 这个面板的核心目标就是“抓取指定时间内的新闻”
- 没有发布时间的内容放进来会破坏用户对时间范围的直觉

### 7.4 候选上限语义

`candidate_limit` 作用在“进入处理队列之前”的候选集合上。

即：

- 先按时间范围过滤
- 再按发布时间倒序截断到 N 条
- 然后才进入提取、富化、入库

这样更直接地控制：

- 处理耗时
- LLM 成本
- 本轮任务规模

### 7.5 停止语义

停止使用**协作式停止**，不做线程强杀。

控制器维护一个 stop flag，在以下边界检查：

- source 开始前
- 每个候选 item 处理前

如果用户点击 `结束处理`：

- 状态先变为 `stopping`
- 当前安全边界结束后停止后续处理
- 最终状态变为 `stopped`

## 8. API 设计

新增一组新闻流手动任务接口：

### `GET /news-run`

返回当前手动任务状态：

- 当前状态
- 当前配置
- 已抓取数
- 已处理数
- 最近错误

### `POST /news-run/start`

请求体包含：

- 时间模式
- 相对或绝对时间范围
- 候选条目上限

行为：

- 若已有运行中的任务，返回冲突错误
- 否则启动一轮任务

### `POST /news-run/stop`

行为：

- 若当前任务在运行，设置停止标志
- 若当前无任务运行，返回当前空闲状态

## 10. 错误处理

前端需要区分：

- 参数校验错误
- 任务已在运行
- 停止请求已受理
- 后端执行失败

后端需要保证：

- 启动参数非法时拒绝启动
- 任务失败时写入 `failed` 和 `last_error`
- 停止请求幂等
- 重复点击开始不会产生并发重复任务

## 13. 风险与边界

### 风险 1：任务状态仅在内存中

如果后端进程重启，当前手动任务状态会丢失。

当前接受这个限制，因为本次目标是快速建立稳定的手动控制能力，而不是任务历史系统。

### 风险 2：page monitor / search 来源耗时不稳定

正文抓取与 LLM 调用都可能拉长单轮任务时间。

通过 `candidate_limit` 可以控制风险。

### 风险 3：发布时间缺失

某些来源可能缺少明确发布时间。首版选择“发布时间缺失则不纳入时间范围任务结果”，以保持行为可解释。

---

## 14. 推荐决策

本次推荐按以下方案落地：

- 首页顶部增加一条新闻流手动处理控制条
- 只控制新闻流
- 支持相对和绝对时间范围
- 候选条目上限作用在进入处理队列前
- 使用单活任务控制器
- 用简要状态展示任务进度
- 用协作式停止而非强杀线程
- 首版以内存状态实现任务控制

这套方案和现有项目结构兼容性高，范围收敛，能在不引入任务中心复杂度的前提下，给出明确可用的手动抓取控制能力。
