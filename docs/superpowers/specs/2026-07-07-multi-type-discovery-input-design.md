# 智能探查多类型输入改造设计

**日期：** 2026-07-07
**状态：** 待用户评审
**项目：** `os-news-tracker` — `DiscoveryPage` 智能探查输入区的多类型路由、命名、校验与日志增强

---

## 1. 背景与目标

当前 `DiscoveryPage` 的 `DiscoveryPanel` 仍然以“单网站 URL 探查”为中心：

- 主输入只接受网站 URL
- `✨ 自动` 只服务网站命名
- `开始探查` 只按网站发现流程发起
- 路由判定主要隐含在后端逻辑里，前端无法显式控制

但现有后端已经开始具备多分支探查能力，用户希望把前端入口升级成一个**显式路由的多类型探查入口**，统一承载四种来源：

- `网页`
- `微信搜索`
- `微信公众号`
- `司内论坛`

本次改造的目标是：

1. 把智能探查输入区升级成“显式路由 + 严格格式输入”的入口
2. 让前端能够明确控制最终路由分支，而不是只把输入交给后端猜
3. 让 `✨ 自动` 按最终路由状态生成名称，而不是只支持网站命名
4. 对输入错误、类型错误、前缀不一致等情况进行即时校验，并在不合法时禁用 `开始探查`
5. 在不重做流程图的前提下，优先把“路由”和“命名”的过程沉淀到日志面板

---

## 2. 已确认约束


| 维度        | 结论                                                        |
| --------- | --------------------------------------------------------- |
| 路由类型      | 固定 4 类：`网页` / `微信搜索` / `微信公众号` / `司内论坛`                   |
| 输入格式      | 严格要求 `XX：XXX`，`XX` 必须是 4 个固定中文前缀之一                        |
| 选择框优先级    | 若用户显式选择类型，则该选择为最高优先级                                      |

| `司内论坛` 输入 | 不要求带 `[km]` / `[iwiki]` 标记，但是没有选择司内论坛的话，就是凭借这两个标识来识别司内论坛的 |

| 测试要求      | 前端本次可以不写测试，以人工验证为主                                        |
| 验收节奏      | 后续 plan 必须包含独立 task；每完成一个模块，需要用户亲自验证通过后才能进入下一步            |

## 3. 非目标

本次不做：

- 流程图节点、边和动画体系的重构
- 新的分步向导或独立探查页面
- 多输入入口并存（例如继续保留旧的“纯 URL”模式）
- 为 `司内论坛` 增加新的高级 MCP 交互配置 UI
- 扩展到 4 类之外的更多来源类型
- 为这次前端改动新增自动化测试

---

## 4. 设计方向

采用“**轻改现有面板**”方案，而不是做新向导。

理由：

- 当前 `DiscoveryPanel` 已有完整的输入区、运行状态、日志区和流程图区骨架
- 用户明确希望“简单改改就行”
- 本次真正重要的是把“路由、校验、命名、状态保存、日志”串稳，而不是重新设计页面结构
- 轻改可以把风险集中在输入与接口层，避免对现有流程图和方式库区域造成不必要扰动

因此，`DiscoveryPage` 与 `DiscoveryPanel` 的整体布局保持不变，只升级顶部控制区的含义与行为。

---

## 5. 输入区信息架构

### 5.1 总体布局

`DiscoveryPanel` 顶部控制区改为两行：

1. **第一行：路由路径选择 + 严格格式输入**
2. **第二行：名称输入 + `✨ 自动` + `开始探查`**

右侧日志面板、下方流程图、方式库列表的总体位置不变。

### 5.2 第一行：路由控制台

新增一个明确带标签的选择框，例如 `路由路径`，固定 4 项：

- `网页`
- `微信搜索`
- `微信公众号`
- `司内论坛`

选择框右侧是主输入框，输入框必须只接受以下 4 种格式之一：

- `网页：<URL>`
- `微信搜索：<关键词>`
- `微信公众号：<账号名或历史链接>`
- `司内论坛：<检索词>`

输入框 placeholder 必须直接给出真实格式示例，而不是泛泛写“请输入内容”。

### 5.3 第二行：名称与主操作

第二行延续现有结构，但语义升级：

- `名称（选填）`
- `✨ 自动`
- `开始探查`

`名称` 仍允许手工覆盖。

`✨ 自动` 不再默认理解为“网站自动命名”，而是“**按最终路由状态自动生成名称**”。

`开始探查` 只有在输入合法且最终路由状态可确定时才允许点击。

### 5.4 轻量提示区

在输入区下方保留一条轻量提示/错误区域，用于即时显示：

- 前缀不合法
- 缺少中文全角冒号 `：`
- 前缀与选择框不一致
- 内容为空
- 类型校验不通过

这块是前端即时反馈，不进入运行日志。

## 6. 路由与校验规则

### 6.1 解析流程

前端需要把主输入框解析成：

- `parsedPrefix`
- `parsedValue`

并据此得出一个“最终路由状态”。

解析步骤如下：

1. 去掉首尾空白
2. 校验是否包含唯一的全角分隔符 `：`
3. 将左侧解析为 `parsedPrefix`
4. 将右侧解析为 `parsedValue`
5. 校验 `parsedPrefix` 是否属于四个固定前缀之一
6. 校验 `parsedValue` 是否非空

### 6.2 最终路由状态

前端引入一个显式的 `resolvedRouteKind`：

- 若用户在选择框中选择了类型，则该值为最高优先级
- 若未来允许“未显式选择”场景，则可回退为程序推断
- 在本次交互中，只要选择框有值，后端就必须按该值执行，不允许再改路由

同时前端还应记录 `routeSource`：

- `explicit`：来自选择框
- `inferred`：来自程序常规判断

本次主要使用 `explicit`，但保留 `inferred` 字段，便于接口向后兼容。

### 6.3 一致性规则

当选择框有值时，输入前缀与选择框必须**严格一致**。

例如：

- 选择 `网页`，输入 `网页：https://openanolis.cn` → 合法
- 选择 `网页`，输入 `微信搜索：openanolis` → 非法

不允许自动改写前缀，不允许用选择框悄悄覆盖输入原文。

### 6.4 类型级别校验

#### `网页`

- `parsedValue` 必须是合法 `http` 或 `https` URL
- 普通文本或无协议域名视为不合法

#### `微信搜索`

- `parsedValue` 必须是非空关键词
- 不接受 URL

#### `微信公众号`

- `parsedValue` 必须满足二选一：
  - 非空公众号名
  - `mp.weixin.qq.com` 历史链接
- 若明显是普通网站 URL，则视为类型错误

#### `司内论坛`

- `parsedValue` 必须是非空检索词
- 不要求带 `[km]` / `[iwiki]`

### 6.5 按钮禁用规则

以下任一情况出现时，`开始探查` 必须禁用：

- 输入框为空
- 输入不满足 `XX：XXX`
- 前缀不在 4 个固定值中
- 内容为空
- 选择框与前缀不一致
- 类型级别校验失败
- 当前已有运行中的探查

`✨ 自动` 也采用同样的合法性前置条件。这样不会出现“能自动命名但不能开始探查”的割裂体验。

## 7. 自动命名规则

`✨ 自动` 的行为统一定义为：

> 依据当前已锁定的最终路由状态，为当前输入生成一个可直接存入名称框的名称。

### 7.1 各类型命名格式

- `网页` → `网站：<LLM 生成名或后备站点名>`
- `微信搜索` → `微信搜索：<关键词>`
- `微信公众号` → `公众号：<账号名或输入值>`
- `司内论坛` → `司内论坛：<检索词>`

### 7.2 生成逻辑

#### `网页`

沿用现有网站命名逻辑：

- 后端抓取页面标题
- 可使用现有 LLM 短标题生成逻辑
- 最终强制包成 `网站：...`

#### 其他三类

不依赖 LLM，直接由前端或后端按固定模板生成：

- `微信搜索：<parsedValue>`
- `公众号：<parsedValue>`
- `司内论坛：<parsedValue>`

### 7.3 用户覆盖

自动生成只负责回填名称框，用户仍可手改。

系统不需要保存“是否为自动命名”的复杂编辑历史，只需保存当前名称值和最近一次自动命名结果即可。

---

## 8. 状态保存设计

### 8.1 前端本地保存

当前 `DiscoveryPanel` 已使用 `localStorage` 保存部分状态。本次需要扩充为保存以下字段：

- `selectedRouteType`
- `rawTypedInput`
- `parsedPrefix`
- `parsedValue`
- `resolvedRouteKind`
- `routeSource`
- `name`
- `runId`
- `selectedNode`
- `expanded`

这样在刷新页面后，用户仍能恢复：

- 选择过的路由路径
- 上次输入的严格格式内容
- 最近一次确定下来的最终路由结果
- 当前名称
- 若 run 仍存在，则继续查看运行状态

### 8.2 后端提交保存

点击 `开始探查` 时，前端不仅提交原始输入，还要把当下已锁定的最终路由状态一并提交给后端。

后端需要能够明确知道：

- 原始输入是什么
- 用户显式选择了什么
- 最终执行的是哪个分支
- 这个分支是显式指定还是程序推断

这样后端才能保证“显式路由优先”不是 UI 文案，而是真正的执行契约。

---

## 9. 开始探查行为

点击 `开始探查` 后，执行顺序如下：

1. 前端完成最终一次校验
2. 锁定当下的最终路由状态
3. 将路由状态写入本地保存
4. 调用后端启动接口，提交原始输入、显式选择、最终路由结果和名称
5. 后端按该已确认分支执行对应探查
6. 前端进入运行态，继续使用现有轮询与日志面板机制

关键约束：

- 如果用户显式选择了路由，后端不允许再覆盖成其他分支
- 只有在未来“未显式选择”的场景中，才允许后端走常规判断

这保证了“路由路径选择框”是真正的控制输入，而不是仅做展示。

## 10. 日志设计

本次改造的重点不是流程图，而是**日志优先**。

### 10.1 日志阶段

日志面板中至少明确区分以下阶段：

- `路由`
- `命名`
- `探查`
- `抓方式`
- `处理`

其中本次新增并要求稳定可见的是：

- `路由`
- `命名`

### 10.2 推荐日志内容

路由相关日志示例：

- `路由 · 输入前缀校验通过`
- `路由 · 选择框命中=微信公众号`
- `路由 · 前缀与选择一致`
- `路由 · 最终分支=微信公众号`
- `路由 · route_source=explicit`

命名相关日志示例：

- `命名 · 自动生成名称=公众号：龙蜥社区`
- `命名 · 自动生成名称=网站：OpenAnolis 博客`

探查启动相关日志示例：

- `探查 · 已按已保存分支启动`
- `探查 · 最终分支=网页`

### 10.3 校验失败与日志边界

前端即时校验失败时，不进入运行态，也不强制写入运行日志。

理由：

- 这些是表单级即时反馈，不属于一次真正开始的探查运行
- 若把半成品校验都塞进日志，会污染“运行轨迹”视图

因此：

- 不合法时：只在输入区提示错误，并禁用按钮
- 合法并开始运行后：日志记录“本次运行所锁定的路由与命名结果”

## 11. 前后端接口边界

本次建议以增量方式改造接口，不重做 discovery 体系。

### 11.1 启动探查接口

当前前端 `startDiscoveryRun()` 仍按网站单 URL 语义工作。本次需要升级为支持多类型输入。

请求体至少应包含：

- `input`
- `selected_route_type`
- `resolved_route_type`
- `route_source`
- `name`
- `force`

后端返回至少应补足：

- `status`
- `run_id`
- `name`
- `route`
- `resolved_route_type`
- `route_source`

前端可以：

- 以 `/discovery/multi-run` 为主入口
- 或让 `/discovery/run` 接受多类型请求后内部转发

无论采用哪种实现方式，接口语义都必须体现“显式路由优先”和“最终分支已锁定”。

### 11.2 自动命名接口

当前 `suggestDiscoveryName()` 只接受网站 URL。本次需要升级为支持按最终路由状态命名。

请求体至少应包含：

- `input`
- `selected_route_type`
- `resolved_route_type`

返回体至少包含：

- `name`
- `resolved_route_type`

对 `网页` 分支可继续使用 LLM 命名；其他三类应直接返回固定模板名称。

## 12. 前端状态模型建议

为避免 `DiscoveryPanel` 继续膨胀为“只有字符串拼接”的状态堆，建议前端引入一个较明确的本地状态模型：

- `selectedRouteType`
- `rawInput`
- `parsedInput`
- `validationError`
- `resolvedRoute`
- `generatedName`
- `runId`
- `runningStatus`

其中 `parsedInput` 可进一步细分为：

- `prefix`
- `value`
- `isValidFormat`

`resolvedRoute` 可进一步细分为：

- `kind`
- `source`
- `isConsistent`

这样可以把：

- 输入解析
- 一致性校验
- 按钮禁用逻辑
- 自动命名入参
- 启动探查入参

统一建立在同一套派生状态之上，而不是在按钮点击时临时拼判断。

## 14. 手动验收标准

本次前端不要求新增测试，验收以手动验证为主。至少覆盖以下场景：

### 14.1 网页

- 选择 `网页`
- 输入 `网页：https://example.com`
- `✨ 自动` 可生成 `网站：...`
- `开始探查` 可点击

### 14.2 微信搜索

- 选择 `微信搜索`
- 输入 `微信搜索：openanolis`
- `✨ 自动` 生成 `微信搜索：openanolis`
- `开始探查` 可点击

### 14.3 微信公众号

- 选择 `微信公众号`
- 输入普通网页 URL 时，按钮禁用并提示类型错误
- 输入公众号名或 `mp.weixin.qq.com` 链接时，允许自动命名和开始探查

### 14.4 司内论坛

- 选择 `司内论坛`
- 输入 `司内论坛：rpm 构建`
- 不要求 `[km]` / `[iwiki]`
- 允许自动命名和开始探查

### 14.5 类型不一致

- 选择 `网页`
- 输入 `微信搜索：openanolis`
- 必须禁用 `开始探查`
- 必须给出明确错误提示

### 14.6 日志

- 启动一次合法探查后，日志中能看到 `路由` 和 `命名` 的独立阶段
- 日志中能看出最终锁定分支，而不是只有最终开始结果

## 15. 实施与验收节奏要求

虽然本 spec 不展开实现 plan，但后续 plan 必须满足以下节奏要求：

1. 必须有至少一个独立 task，聚焦完成一个明确模块功能
2. 不允许把所有前端改动一次性堆完再统一验收
3. 每完成一个模块后，需要用户亲自使用并确认通过，才进入下一步
4. 前端本次可以不写测试，但不能跳过人工验证门槛
5. 不要吧Task分的太散，本身不是什么大人物，几个Task足矣

推荐后续按以下模块切分：

1. 输入区结构与即时校验
2. 自动命名与本地状态保存
3. 启动探查接线与日志补强

---

## 16. 结论

本次改造不是重新设计站点发现页面，而是在现有 `DiscoveryPanel` 基础上，把“单 URL 探查”升级成“多类型、显式路由、严格格式、日志优先”的智能探查入口。

落地后的核心体验应当是：

- 用户先明确声明“我要探查哪一类来源”
- 输入内容必须与该声明严格一致
- 系统在开始前就能给出清晰、可预期的命名和校验反馈
- 一旦开始探查，前后端都明确知道最终执行的是哪个分支
- 即使流程图暂时不扩展，日志也能清楚还原“如何路由、如何命名、如何启动”
